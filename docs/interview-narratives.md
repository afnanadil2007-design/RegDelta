# Two engineering stories

Short, factual accounts for discussing RegDelta in an interview. Each one
links to the commit or result it rests on; nothing here is a claim the
repository cannot show.

## 1. The ORM package that was never committed

**Situation.** The public snapshot (`f4a4b57`) built its frontend fine, but the
backend could not start: `alembic upgrade head` failed with
`ModuleNotFoundError: No module named 'app.db.models'`, mypy reported 17
import errors in 13 files, and every test module that touched the database
failed to collect. The code imported a package that was not in the repository.

**Cause.** `.gitignore` line 25 read `models/`. It was meant for downloaded
model weights, but an unanchored pattern matches a directory of that name at
any depth, so it also matched `backend/app/db/models/`. The package had
worked on the author's machine and had simply never been tracked:
`git log --all -- 'backend/app/db/models*'` is empty, and
`git check-ignore -v backend/app/db/models/corpus.py` names the rule.

**Recovery first.** Before writing anything I searched for the originals: the
filesystem (including bytecode caches), Docker images and volumes, and the
history of earlier sessions. None held a copy, so the package had to be
reconstructed, and the reconstruction had to be checked rather than trusted.

**Reconstruction.** The models were derived from the evidence the repository
did contain: the autogenerated migration `0002` (types, nullability, indexes,
constraint names, foreign-key actions, enum labels), migration `0003`,
attribute usage across the code, and the test contracts for defaults. Two
checks prove the result matches the schema the migrations build:

- `alembic check` against a database built from the migrations reports no
  differences, with type and server-default comparison on;
- `backend/tests/test_model_migration_parity.py` covers what autogenerate
  ignores: enum labels, CHECK constraints, HNSW and GIN index methods and
  operator classes, and generated-column expressions.

**Prevention.** The ignore rules are anchored to the repository root
(`/models/`, `/.cache/`), virtualenv debris that had been tracked under
`backend/` was removed, and the parity test also fails if the model sources
are ever ignored again.

**What it taught.** A clean CI run on one half of a repository says nothing
about the other half; an ignore rule is code and deserves a test; and a
reconstruction is only as good as the comparison that checks it.
Commit: `941d9d1` (*fix(db): restore the ORM package lost to an unanchored
ignore rule*).

## 2. Paying for a reranker: quality, refusal and latency

**Question.** Search fuses a dense and a lexical ranking with reciprocal
rank fusion (RRF); an optional cross-encoder rereads the candidates. Is the
cross-encoder worth what it costs, and can its score decide when to say "no
passage is relevant"?

**Method.** One fixed manifest of 120 queries from 60 citations (seed
20261015), half the citing paragraph and half the bare reference, plus a
refusal suite of 15 questions to refuse and 15 on-topic controls. Every mode
runs through the API's own `retrieve()` on the same ids; intervals are 95%
bootstraps that resample citing circulars, and mode differences are paired
on identical queries. Labels are template-derived from the synthetic
corpus, so this compares configurations; it does not estimate quality on
real SEBI circulars.

**Result** (`evaluation/results/retrieval/2026-10-15-ablation/`):

| | Hybrid (RRF) | Hybrid + rerank | Paired difference |
|---|---:|---:|---|
| Recall@10 | 0.650 | 0.758 | +0.108 (+0.059 to +0.164) |
| MRR@10 | 0.388 | 0.545 | +0.157 (+0.108 to +0.201) |
| Identifier Recall@1 | 0.467 | 0.900 | |
| Semantic Recall@10 | 0.317 | 0.517 | |
| Median latency per query | 47 ms | 56 s | |

Most of the gain is at the top of identifier queries: RRF already finds the
cited circular (Recall@10 0.983) but often below a sibling with a similar
number, and the cross-encoder puts it first. Semantic queries stay hard for
every mode (best MRR@10 0.142), because 300 circulars from eight templates
are full of near-duplicates that answer a paragraph equally well.

**Refusal.** Only the reranked mode can refuse: its score reads the query
and the passage together, where RRF's is a function of ranks alone. It refused all 15 questions it should refuse (best passage
score ≤ 0.011) and none of the 15 controls or 120 labelled queries (lowest
best-passage score 0.993), so the 0.35 threshold, set before the run and
not tuned on it, sits in a wide gap. That gap is partly the suite's doing:
it has no near-miss questions, and 15 + 15 questions leave Wilson intervals
of about 0.80–1.00 and 0.00–0.20.

**Two bugs the measurement caught.** An earlier refusal suite answered "What
is the capital of France?": the code applied a sigmoid on top of the one
`CrossEncoder.predict` already applies, squeezing every score into
(0.5, 0.731). Ranking metrics were unaffected, so nothing looked wrong until
refusal was measured; a test on the real model now asserts that an
unrelated query scores below the threshold. Later, the evaluation runner itself
counted the 15 controls as out-of-scope questions and reported "15 of 30
refused". The per-query rows were right, so the summary was recomputed from
them (`--resummarise`, commit `87ccc92`) rather than rerun, and the
correction is recorded with the result.

**Decision.** The cost is about a thousandfold per query on this laptop's
CPU: 47 ms against a 56 s median, measured under load. So Hybrid is the
default on the search page, and the reranked mode is opt-in, with a running
clock and a Cancel button. Assessments use the cross-encoder for clause
retrieval because there the order of the clauses is the product, and the
run's call and time budgets bound the cost.

**What it taught.** Measure refusal beside ranking, not inside it; resample
the unit that is actually independent; and read your own denominators as
sceptically as anyone else's.
